# Завдання: Виявлення та усунення витоків пам'яті (Memory Leaks)

## Мета завдання
Навчитися створювати штучний виток пам'яті за допомогою `Activity Context`, візуалізувати та виявляти його за допомогою професійного інструменту **Memory Profiler** в Android Studio, а також правильно виправляти його у коді.

---

## Частина 1: Створення витоку пам'яті

1. **Створення синглтону:**
   У вашому проекті створіть новий об'єкт-синглтон `UserTracker`:
   ```kotlin
   object UserTracker {
       private val listeners = mutableListOf<Context>()

       fun register(context: Context) {
           listeners.add(context)
       }

       fun getListenersCount(): Int = listeners.size
   }
   ```

2. **Реєстрація у MainActivity:**
   * У методі `onCreate()` вашої `MainActivity` зареєструйте поточний екран, передавши `this`:
     `UserTracker.register(this)`
   * Додайте логування (через Timber або `Log.d`), яке виводить поточну кількість слухачів: 
     `Timber.d("Зареєстровано слухачів у UserTracker: ${UserTracker.getListenersCount()}")`

3. **Відтворення витоку:**
   * Запустіть застосунок на пристрої чи емуляторі.
   * Переверніть телефон (змініть орієнтацію екрану) 5 разів поспіль.
   * Подивіться в Logcat: ви побачите, що кількість слухачів зростає з кожним поворотом (1, 2, 3, 4, 5...), хоча активним є лише один екран!

---

## Частина 2: Візуалізація витоку через Memory Profiler в Android Studio

Тепер ми наочно підтвердимо наявність витоку пам'яті за допомогою вбудованого аналізатора пам'яті Android Studio.

1. **Відкриття Profiler:**
   * У нижній панелі Android Studio відкрийте вкладку **Profiler** (або через головне меню `View -> Tool Windows -> Profiler`).
   * Оберіть запущений процес вашого застосунку та натисніть на графік **Memory**.

2. **Знімок оперативної пам'яті (Dump Java Heap):**
   * Зробіть ще 3-4 повороти екрану пристрою.
   * У панелі Profiler натисніть кнопку **Capture heap dump** (іконка із зображенням зліпка пам'яті / відерця) та натисніть **Record**.
   * Дочекайтеся, поки Android Studio збереже та проаналізує зріз оперативної пам'яті.

3. **Аналіз об'єктів у пам'яті:**
   * У верхньому рядку пошуку панелі Heap Dump введіть назву вашого класу: `MainActivity`.
   * Подивіться на колонку **Count** (кількість екземплярів). Ви побачите, що в пам'яті одночасно перебуває кілька об'єктів `MainActivity` (хоча на екрані користувач бачить лише один!).
   * Клікніть на один зі старих (знищених) екземплярів `MainActivity` у списку та розгорніть нижню панель **References** (або GC Roots).
   * Знайдіть у списку посилань поле `UserTracker.listeners` — це і є те саме "мертве" посилання, яке не дає сміттєзбирачу (Garbage Collector) видалити закритий екран з RAM.

---

## Частина 3: Виправлення витоку пам'яті

Тепер виправте виток пам'яті у свій код. Випробуйте два можливі способи рішення:

### Спосіб A: Використання правильного типу Context
Якщо синглтону `UserTracker` не потрібні UI-функції конкретного екрану, зберігайте у ньому глобальний контекст застосунку:
```kotlin
fun register(context: Context) {
    listeners.add(context.applicationContext)
}
```
* **Перевірка:** Очистіть список `listeners`, знову зробіть 5 поворотів екрану та зніміть **Heap Dump** у Profiler. Переконайтеся, що кількість об'єктів `MainActivity` у пам'яті тепер дорівнює **1**.

### Спосіб B: Вчасне видалення слухача (Unregister)
Якщо синглтону дійсно потрібен був `Activity Context`, додайте у `UserTracker` метод видалення:
```kotlin
fun unregister(context: Context) {
    listeners.remove(context)
}
```
* **Перевірка:** У вашій `MainActivity` перевизначте метод `onDestroy()` і викликайте `UserTracker.unregister(this)`. Проведіть експеримент з поворотом екрану ще раз і переконайтеся через Profiler, що старі Activity більше не зависають у пам'яті.

Успіхів! Уміння знаходити витоки пам'яті через Memory Profiler — це одна з найцінніших практичних навичок Android-розробника.
