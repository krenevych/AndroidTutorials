# Завдання: «ПриватБанк — валюти» з Room та фоновою синхронізацією

## Мета завдання

Розширити застосунок із попереднього завдання: зберігати отримані курси валют у **Room**, читати їх через **Flow** та оновлювати базу у фоні за допомогою **WorkManager**. Навчитися показувати збережені дані без Інтернету та відокремлювати відображення списку від його мережевого оновлення.

---

## Початкові умови

Використайте власний розв'язок завдання [«ПриватБанк — валюти» (Retrofit та MVVM)](02_RetrofitTask.md).

Перед виконанням опрацюйте туторіали:

* [«Локальна база даних: Room Database»](../../Documentation/09_Data/03_RoomDB.md).
* [«Гарантоване фонове виконання: WorkManager»](../../Documentation/08_SystemComponents/03_WorkManager.md).

Залишаємо той самий архівний API, формат дати `dd.MM.yyyy`, вибір дати та список валют. Змінюємо шлях отримання даних:

```text
WorkManager → Worker → Retrofit / API → Room → Flow → ViewModel → Compose
```

**Список на екрані завжди читається з Room.** Відповідь Retrofit спочатку зберігається у базі; після цього Room сповіщає підписників про зміни.

---

## Опис та вимоги до застосунку

1. **Локальне збереження:** курси різних дат зберігаються у базі та доступні після перезапуску застосунку.
2. **Вибір дати:** екран показує збережені курси для обраної дати. Якщо їх немає, відображає повідомлення «Курси за цю дату ще не завантажені».
3. **Кнопка «Оновити»:** ставить одноразове завдання WorkManager на завантаження обраної дати у базу.
4. **Періодичне оновлення:** WorkManager приблизно раз на годину завантажує курси **на поточну дату**. Дату Worker визначає під час кожного виконання, щоб наступного дня оновлювалися вже нові курси.
5. **Офлайн-режим:** відсутність мережі не заважає переглядати вже збережені курси. Помилка оновлення не очищує базу та не приховує попередній список.
6. **Збереження стану:** поворот екрана не скидає обрану дату та не створює дублікати фонових завдань.

Курси купівлі й продажу залишаються необов'язковими: для відсутніх значень показуйте «—», як у попередньому завданні.

## Етапи виконання завдання

### Частина 1: Створення локальної бази Room

1. Підключіть Room та KSP за туторіалом. Для цього навчального прикладу використовуйте `exportSchema = false`.
2. Створіть сутність `ExchangeRateEntity` з полями:

   | Поле | Тип | Призначення |
   | --- | --- | --- |
   | `date` | `String` | Дата курсів у форматі `dd.MM.yyyy` |
   | `currency` | `String` | Код валюти |
   | `baseCurrency` | `String` | Базова валюта, наприклад `UAH` |
   | `purchaseRate` | `Double?` | Курс купівлі ПриватБанку |
   | `saleRate` | `Double?` | Курс продажу ПриватБанку |

3. Задайте **складений первинний ключ із дати та коду валюти**:

   ```kotlin
   @Entity(tableName = "exchange_rates", primaryKeys = ["date", "currency"])
   ```

   Наприклад, `USD` за дві різні дати — це два різні записи. Повторне завантаження `USD` за ту саму дату має оновити запис, а не створити дублікат.

4. Створіть `ExchangeRateDao`. Додайте метод збереження списку через `@Upsert` із `suspend` та реактивний запит:

   ```kotlin
   @Query("SELECT * FROM exchange_rates WHERE date = :date ORDER BY currency ASC")
   fun observeRates(date: String): Flow<List<ExchangeRateEntity>>
   ```

5. Створіть `ExchangeDatabase` та спільний екземпляр бази за прикладом туторіалу. Використайте `AndroidSQLiteDriver`.

### Частина 2: Завантаження та збереження у Worker

1. Підключіть WorkManager та створіть клас `ExchangeRatesSyncWorker`, успадкований від `CoroutineWorker`.
2. Передбачте необов'язковий вхідний параметр **`date`** через `inputData`. Якщо дату передано — завантажуйте її; якщо параметра немає — визначайте поточну дату на початку `doWork()`.
3. Адаптуйте метод Retrofit до роботи з корутинами: замість `Call<ExchangeArchiveResponse>` використайте `suspend`-метод із результатом `Response<ExchangeArchiveResponse>`. Перевірку HTTP-статусу та тіла відповіді перенесіть із callback у Worker.
4. Усередині `doWork()` отримайте API та DAO через спільні налаштування мережі й бази з використанням `applicationContext`. Worker повинен працювати без відкритої Activity та без доступу до ViewModel.
5. Завантажте курси, перетворіть елементи `exchangeRate` на `ExchangeRateEntity` та збережіть їх через DAO. Дату для записів беріть із перевіреної відповіді API; вона має відповідати запитаній даті. Елементи без коду валюти пропускайте.
6. Повертайте **`Result.success()` лише після завершення запису у Room**. Для тимчасової помилки мережі або сервера використовуйте `Result.retry()`, для некоректних вхідних даних чи відповіді — `Result.failure()`. У разі порожньої коректної відповіді передайте повідомлення «Сервер не повернув курсів», залишивши попередні записи без змін.

> 💡 **Важливо:** не залишайте всередині `doWork()` виклик `enqueue()` з негайним поверненням `Result.success()`. Тоді WorkManager вважатиме завдання виконаним ще до отримання відповіді та запису в базу. `CoroutineWorker` має дочекатися обох операцій. Скасування корутини не перетворюйте на `Result.retry()`.

### Частина 3: Періодичне та ручне оновлення

1. Створіть `Constraints` із вимогою **`NetworkType.CONNECTED`**. Застосуйте її до обох типів завдань.
2. Налаштуйте періодичне завдання:

   ```kotlin
   val periodicRequest =
       PeriodicWorkRequestBuilder<ExchangeRatesSyncWorker>(1, TimeUnit.HOURS)
           .setConstraints(constraints)
           .build()

   WorkManager.getInstance(context.applicationContext).enqueueUniquePeriodicWork(
       "exchange_rates_periodic",
       ExistingPeriodicWorkPolicy.KEEP,
       periodicRequest
   )
   ```

3. Реєструйте його під час ініціалізації застосунку. Завдяки сталому імені та `KEEP` повторний запуск застосунку не створить ще одну періодичну задачу. **Не передавайте фіксовану дату в періодичний запит:** інакше він щодня завантажуватиме той самий архівний день.
4. Для кнопки «Оновити» створюйте `OneTimeWorkRequest` того самого Worker, передаючи обрану дату через `workDataOf("date" to selectedDate)`.
5. Ставте одноразову задачу через `enqueueUniqueWork()` з ім'ям на кшталт `"exchange_rates_$selectedDate"` та політикою `ExistingWorkPolicy.KEEP`, щоб повторні натискання не дублювали незавершений запит цієї дати.

**Періодичний запуск не є точним таймером.** Мінімальний інтервал WorkManager — 15 хвилин, а фактичний час виконання залежить від мережі та системних обмежень. Одноразове завдання також може очікувати на виконання умов. Не реалізовуйте періодичність власним циклом із `delay()`. [Налаштування WorkRequest](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work), [унікальні завдання](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/manage-work).

### Частина 4: ViewModel та екран, який читає Room

1. Приберіть прямий виклик Retrofit із ViewModel. Вибір дати має перемикати підписку на `observeRates(date)`; для цього можна використати `flatMapLatest` та `stateIn`.
2. Зберігайте обрану дату у ViewModel. Передавайте у Compose стан списку з Room через `StateFlow` та збирайте його через `collectAsStateWithLifecycle()`.
3. Кнопка «Оновити» лише ставить одноразове завдання у WorkManager. Після завершення синхронізації список оновлюється через Flow з Room, без повторного ручного читання бази.
4. Окремо спостерігайте за `WorkInfo` одноразового завдання для обраної дати. Показуйте «Очікує мережі / запуску», «Оновлюється», результат або помилку, зберігаючи на екрані наявні курси. Для повідомлень Worker можна використати `outputData`; сам список валют через нього не передавайте.
5. При зміні дати відображайте лише її записи. Періодичне оновлення поточної дати не повинне підміняти список обраної архівної дати.
6. Не скасовуйте роботу WorkManager у `onCleared()` ViewModel: фонова синхронізація має власний життєвий цикл і може працювати після закриття екрана.

### Частина 5: Практична перевірка

1. **Шлях даних:** натисніть «Оновити» та відкрийте таблицю в Database Inspector. Переконайтеся, що записи з'явилися у Room, а потім відобразилися на екрані.
2. **Відсутність дублікатів:** кілька разів оновіть ту саму дату. Кількість записів для неї не повинна зростати через повторні вставки.
3. **Різні дати:** завантажте курси за два дні. Перемикайте дату та перевірте, що кожен список читається зі своєї вибірки, а дані іншої дати залишаються у базі.
4. **Офлайн-режим:** вимкніть Інтернет, перезапустіть застосунок і виберіть уже завантажену дату. Список має залишитися доступним. Одноразове оновлення повинне очікувати мережі; після її повернення — виконатися.
5. **Поворот екрана:** поверніть пристрій під час оновлення та після нього. Дата й список зберігаються, а кількість завдань WorkManager не збільшується.
6. **Періодична синхронізація:** перевірте її реєстрацію у **App Inspection → Background Task Inspector**. Для швидкої перевірки коду Worker використайте одноразове оновлення; перевірку фактичного повторного запуску проведіть окремо, з урахуванням системних затримок. Після успішного циклу періодична задача знову очікує наступного запуску, а не переходить у кінцевий стан `SUCCEEDED`.
7. **Помилка оновлення:** зімітуйте помилку відповіді API та перевірте, що раніше збережені курси не видаляються. Якщо сервер повернув порожній список, покажіть відповідне повідомлення; за наявності старих даних позначте їх як раніше збережені.
