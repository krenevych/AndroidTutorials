# Фінальний проєкт: «Біржа криптовалют»

## Мета проєкту

Розробіть інформаційний Android-застосунок, який показує вартість **30 криптовалют у доларах США**, зберігає отримані дані локально та періодично оновлює їх у фоні.

Об'єднайте в одному проєкті **чисту архітектуру**, **MVVM**, **Retrofit**, **Room**, **WorkManager** та **Jetpack Compose**. Застосунок повинен коректно працювати після повороту екрана та дозволяти переглядати раніше завантажені дані без Інтернету.

**Формат роботи — команда з двох учасників.**

## Джерело даних та зображення

### API криптовалют

Для отримання даних використайте **CoinDesk Data API**. [Офіційна документація](https://developers.coindesk.com/documentation/data-api/introduction).

Для отримання рейтингу використайте **Top List General**:

```text
Базова адреса: https://data-api.coindesk.com/
Ресурс:        asset/v1/top/list
```

У [документації Top List General](https://developers.coindesk.com/documentation/data-api/asset_v1_top_list) налаштуйте запит на **перші 30 криптовалют за спаданням ринкової капіталізації** з цінами у USD. Перед написанням моделей виконайте запит із власним ключем у API Explorer і перегляньте фактичну структуру JSON. Опис доступних груп даних та рейтингових запитів наведений у [розділі Asset](https://developers.coindesk.com/documentation/data-api/asset).

### Ключ доступу

Зареєструйте ключ у кабінеті провайдера та перевірте доступність запиту й ліміти вашого плану.

Передавайте ключ заголовком `Authorization: Apikey YOUR_API_KEY`. Зчитуйте значення з локальної конфігурації, наприклад `local.properties`, виключеної з Git. У README опишіть налаштування та наведіть шаблон із порожнім значенням. **Не додавайте справжній ключ у коміти, логи чи демонстраційне відео.** [Автентифікація API](https://developers.coindesk.com/documentation/data-api/introduction).

### Зображення криптовалют

Для завантаження та відображення зображень використайте **Coil 3** та компонент `AsyncImage`. [Coil для Compose](https://coil-kt.github.io/coil/compose/).

Для завантаження через мережу Coil 3 потребує окремого мережевого модуля. Приклад залежностей:

```kotlin
val coilVersion = "3.6.3"
implementation("io.coil-kt.coil3:coil-compose:$coilVersion")
implementation("io.coil-kt.coil3:coil-network-okhttp:$coilVersion")
```

Використовуйте однакову версію обох модулів та звіряйте налаштування з [документацією Coil](https://coil-kt.github.io/coil/network/).

Завантажуйте зображення за адресою з отриманих метаданих — полем `LOGO_URL`. Передбачте заглушку на час завантаження та випадок відсутнього або недоступного зображення. [Метадані активів](https://developers.coindesk.com/documentation/data-api/asset_v2_metadata).

## Обов'язковий функціонал

1. **Список криптовалют (`LazyColumn`).** Для кожної валюти покажіть назву, символ, зображення та ціну в USD. Відображайте порядок отриманого рейтингу та використовуйте стабільний ідентифікатор для `key`.
2. **Ручне оновлення.** Кнопка «Оновити» запускає одноразове завдання WorkManager, яке отримує нові дані та записує їх у Room.
3. **Періодичне оновлення.** WorkManager оновлює дані у фоні з інтервалом від 15 хвилин, обраним з урахуванням лімітів API. Для навчального проєкту можна використати одну годину.
4. **Офлайн-перегляд.** Після першого успішного завантаження список і ціни доступні без Інтернету, зокрема після перезапуску. Для зображень без доступного кешу достатньо заглушки.
5. **Стан оновлення.** Покажіть час останнього успішного збереження даних, очікування мережі, виконання оновлення та повідомлення про помилку. Збережений список залишається доступним під час наступних оновлень.
6. **Обробка відсутніх даних.** До першого завантаження покажіть відповідний стан. Відсутню ціну позначайте як «Немає даних», а не як `0`. Не встановлюйте однакове округлення, яке перетворює всі малі ціни на `0.00`.
7. **Поворот екрана та зміни конфігурації.** Збережіть стан списку, його прокрутку та активне оновлення при повороті. Перевірте також зміну світлої й темної теми. Новий екземпляр екрана не повинен створювати дублікати запитів або періодичних задач.

## Вимоги до архітектури

Виділіть три шари. Для навчального проєкту достатньо пакетів `data`, `domain` та `presentation` в одному Gradle-модулі; окремі модулі можна створити за бажанням.

| Шар | Відповідальність |
| --- | --- |
| `domain` | Модель криптовалюти, інтерфейс репозиторію та сценарії отримання збережених даних і синхронізації. Не залежить від Android UI, Room, Retrofit чи WorkManager. |
| `data` | API-інтерфейс, DTO, Room Entity, DAO та реалізація репозиторію. Перетворює мережеві й локальні моделі на моделі предметної області. |
| `presentation` | ViewModel, стан екрана та Compose-компоненти. Показує дані й передає дії користувача. Не виконує SQL або HTTP-запитів. |

Worker є інфраструктурним компонентом: він викликає сценарій синхронізації, який через репозиторій завантажує та зберігає дані. Постановку завдань WorkManager також відокремте від composable. Залежності можна передавати вручну через спільний контейнер застосунку; окремий DI-фреймворк не є обов'язковим.

```text
WorkManager → Worker → синхронізація → репозиторій → API → Room
Room → Flow → репозиторій → ViewModel → StateFlow → Compose
```

**Єдине джерело списку та цін для UI — Room.** Відповідь Retrofit не повинна напряму підміняти список у ViewModel. DTO, Entity та модель `domain` мають бути окремими типами.

## Збереження даних та синхронізація

### Room

* Використовуйте стабільний ID активу з API як первинний ключ. Повторне оновлення не повинне створювати дублікати.
* Зберігайте поля, потрібні для офлайн-відображення: ID, назву, символ, адресу зображення, ціну, місце в отриманому рейтингу та час успішного оновлення. Типи полів оберіть відповідно до моделей; додаткові конвертери дати для цього завдання не обов'язкові.
* Повертайте список із DAO як `Flow` із сортуванням за збереженим місцем у рейтингу.
* Після успішного отримання нового коректного списку оновлюйте його **в одній транзакції**. Валюти, які вийшли з топ-30, не повинні накопичуватися у поточному рейтингу. Під час помилки чи некоректної відповіді збережіть попередні записи.
* Не очищуйте таблицю до завершення мережевого запиту. Час успішного оновлення змінюйте лише разом зі збереженням нового результату.

### WorkManager

* Реалізуйте `CoroutineWorker`, який очікує завершення мережевого запиту та запису у базу, а потім повертає результат. Не запускайте callback-запит із негайним поверненням `Result.success()`.
* Додайте умову `NetworkType.CONNECTED` до одноразової та періодичної роботи.
* Періодичне завдання реєструйте через `enqueueUniquePeriodicWork()` зі сталим іменем та політикою `KEEP`. Ручне оновлення також захистіть від дублювання незавершених задач.
* Для тимчасових мережевих помилок використовуйте повторну спробу з backoff. Помилки ключа чи прав доступу показуйте окремо; не повторюйте їх нескінченно. При перевищенні ліміту API враховуйте його правила повторних запитів.
* Worker має працювати без відкритого екрана та без посилання на Activity або ViewModel. Закриття екрана не повинне скасовувати заплановану фонову синхронізацію.
* WorkManager планує відкладену роботу: інтервал не гарантує виконання в точну хвилину. Показуйте фактичний час оновлення даних. [Налаштування та обмеження WorkRequest](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work).

## Командна робота

1. Виконуйте проєкт **удвох** та завчасно узгодьте структуру шарів, модель `domain` та інтерфейс репозиторію.
2. Розділіть реалізацію. Наприклад, один учасник працює над API, Room і Worker, інший — над сценаріями `domain`, ViewModel та Compose. Остаточний розподіл оберіть самостійно.
3. Кожен учасник повинен зробити власні змістовні коміти з реалізацією своєї частини. Історія Git має показувати внесок **обох учасників**.
4. Перед здачею перегляньте код одне одного. **Кожен повинен уміти пояснити весь шлях даних**, зокрема частину, реалізовану напарником.

## Перевірка готового застосунку

| Сценарій | Очікуваний результат |
| --- | --- |
| Перший запуск із мережею та доступом до API | Дані отримані, записані у Room та показані списком із зображеннями або заглушками. |
| Повторне ручне оновлення | Ціни й рейтинг оновлюються, дублікати не накопичуються. |
| Зміна складу топ-30 у тестовій відповіді | Поточний рейтинг відповідає новому набору, старі учасники рейтингу не залишаються зайвими рядками. |
| Поворот під час і після оновлення | Стан та прокрутка збережені, додаткові завдання не створені. |
| Зміна системної теми | Екран коректно відображається, дані залишаються доступними. |
| Перезапуск без Інтернету після успішного завантаження | Збережені ціни доступні; для некешованих зображень показані заглушки. |
| Оновлення без мережі або помилка API | Наявний список залишається, користувач бачить стан очікування чи помилку. |
| Повторне відкриття застосунку | У WorkManager залишається одна періодична задача з обраним іменем. |

Для перевірки Room використайте **Database Inspector**, а для реєстрації та станів задач — **Background Task Inspector**. Якщо реальний API не повертає потрібний граничний випадок, перевірте його на локальній тестовій відповіді. Окремо перевірте перетворення DTO з відсутніми ціною чи зображенням та збереження попередньої бази після невдалого оновлення.

Покажіть наявність періодичного завдання в інспекторі; для демонстрації виконання Worker можна використати ручне одноразове оновлення, не чекаючи всього інтервалу.

## Додаткові можливості (за бажанням ⭐)

* Пошук за назвою чи символом серед локально збережених валют.
* Екран деталей валюти з додатковими показниками з API.
* Обране зі збереженням вибору користувача після синхронізації.
* Тести репозиторію: невдала синхронізація зберігає кеш, повторна не створює дублікатів, новий рейтинг замінює попередній атомарно.
