# Завдання: "Живий" пошук у реальному часі за допомогою операторів Kotlin Flow

## Мета завдання
Навчитися використовувати потужний набір операторів **Kotlin Flow** (`debounce`, `filter`, `distinctUntilChanged`, `map`, `catch`, `flowOn`) для побудови ефективного "пошуку на льоту" (Search-as-you-type) без створення зайвого навантаження на базу даних чи мережу.

---

## Опис проблеми

У класичному підході, якщо підключити слухач введення тексту `TextWatcher` до поля `EditText`, завантаження даних викликається **на кожну введену чи видалену літеру**. 

Якщо користувач швидко вводить слово з 10 букв "Володимир", застосунок зробить **10 послідовних важких запитів** у базу даних чи мережу ("В", "Во", "Вол", "Воло"...), що спричинить гальмування UI, перевитрату трафіку та батареї.

---

## Опис та вимоги до застосунку

На екрані знаходяться:
1. **Поле введення пошукового запиту** (`etSearchQuery`).
2. **Список результатів** (`tvSearchResults` або `RecyclerView`).
3. **ProgressBar завантаження** (`progressBar`).

---

## Оператори Flow, які необхідно задіяти

Для розв'язання проблеми надмірного спаму запитами, ланцюжок Flow у `ViewModel` повинен містити такі оператори:

1. **`debounce(400)`** — чекає паузу в 400 мілісекунд після останнього введеного символу. Запит відправляється тільки тоді, коли користувач робить паузу у введенні!
2. **`filter { query -> query.length >= 3 }`** — відсікає занадто короткі запити (не шукає, якщо введено менше 3 символів).
3. **`distinctUntilChanged()`** — запобігає повторним однаковим запитам (якщо користувач швидко ввів літеру і видалив її назад, залишивши той самий текст).
4. **`map { query -> repository.search(query) }`** — викликає метод пошуку у шарі `Model`.
5. **`flowOn(Dispatchers.IO)`** — виконує пошук у фоновому потоці.
6. **`catch { e -> ... }`** — перехоплює можливі помилки та запобігає крашу.

## Етапи виконання завдання

### Частина 1: Створення макету та шару Model (`SearchRepository`)
1. Створіть клас `SearchRepository`.
2. Додайте функцію `search(query: String): List<String>`, яка імітує пошук у базі даних (наприклад, шукає збіги серед списку країн чи міст) та робить затримку `Thread.sleep(500)` або `delay(500)`.

---

### Частина 2: Отримання Flow з EditText та побудова ланцюжка
1. У `SearchViewModel` перетворюйте текстові зміни з `EditText` у `StateFlow<String>` (наприклад, за допомогою `MutableStateFlow`).
2. Побудуйте асинхронний ланцюжок обробки за допомогою операторів Flow:
   ```kotlin
   val searchResults = searchQueryFlow
       .debounce(400)
       .filter { query -> query.trim().length >= 3 }
       .distinctUntilChanged()
       .map { query -> searchRepository.search(query) }
       .flowOn(Dispatchers.IO)
       .catch { e -> emit(emptyList()) }
       .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), emptyList())
   ```

---

### Частина 3: Підписка у View (`MainActivity`) та тестування
1. У `MainActivity` підключіть слухач введення тексту до `etSearchQuery` (наприклад, `doOnTextChanged { text, ... -> viewModel.onQueryChanged(text.toString()) }`).
2. Підпишіться на `viewModel.searchResults` через `lifecycleScope.launch` та відображайте знайдений список у UI.
3. **Проведіть практичне тестування:**
   * **Тест 1 (Debounce):** Почніть швидко друкувати слово "Україна". Переконайтеся в Logcat, що запит у базу відправляється **лише один раз** після того, як ви зупинилися на 400 мс!
   * **Тест 2 (Filter):** Введіть 1 або 2 символи ("Ук"). Переконайтеся, що пошук не викликається.
   * **Тест 3 (Distinct):** Введіть "Київ", швидко витріть останню букву і знову введіть "в" ("Киї" -> "Київ"). Переконайтеся, що повторний однаковий запит не надсилається.
