# Завдання: Дослідження відмінностей між Холодними (Flow) та Гарячими (StateFlow) потоками

## Мета завдання
На практиці відчути принципову різницю між **холодним реактивним потоком (`Flow`)** та **гарячим потоком стану (`StateFlow`)**. Дослідити поведінку генерації даних (на прикладі послідовності Фібоначчі) за допомогою ручного керування підпискою/скасуванням через кнопки на екрані, а також перевірити поведінку при змінах конфігурації (поворот екрану або зміна теми).

Ви можете завантажити або склонувати заготовку проекту з GitHub:
* 📦 **Початковий проект:** [krenevych/Concurrency (гілка main, модуль flowcomparison)](https://github.com/krenevych/Concurrency/tree/main/flowcomparison)
* 💡 **Приклад розв'язку:** [krenevych/Concurrency (гілка flowcomparison_end, модуль flowcomparison)](https://github.com/krenevych/Concurrency/tree/flowcomparison_end/flowcomparison)

На екрані `MainActivity` знаходяться дві кнопки:
1. **Кнопка "Підписатися" (`btnSubscribe`)** — запускає корутину збирання даних з потоку (`collect`) усередині `repeatOnLifecycle`.
2. **Кнопка "Скасувати" (`btnCancel`)** — скасовує активну корутину підписки (`fibonacciJob?.cancel()`).

У `MainActivity` створіть змінну `private var fibonacciJob: Job? = null` для керування підпискою:

```kotlin
// Клік кнопки "Підписатися"
binding.btnSubscribe.setOnClickListener {
    if (fibonacciJob != null) {
        Toast.makeText(this, "Already subscribed", Toast.LENGTH_SHORT).show()
        return@setOnClickListener
    }

    fibonacciJob = lifecycleScope.launch {
        repeatOnLifecycle(Lifecycle.State.RESUMED) {
            viewModel.fib.collect { elem: BigInteger ->
                Log.d("EEEE", "Activity : $elem")
            }
        }
    }
}

// Клік кнопки "Скасувати"
binding.btnCancel.setOnClickListener {
    fibonacciJob?.cancel()
    fibonacciJob = null
}
```

## Етапи виконання та дослідження

### Експеримент 1: Дослідження Холодного потоку (`Flow`)

1. Усередині `CalculationViewModel` оголосіть **холодний потік** `val fib: Flow<BigInteger> = flow { ... }`.
2. Усередині білдера `flow { ... }` реалізуйте безкінечний цикл генерації чисел Фібоначчі (`1, 1, 2, 3, 5, 8, 13...`) із затримкою `delay(500.milliseconds)` та логуванням:
   `Log.i("EEEE", "ViewModel: $f1")`
3. Запустіть додаток і проведіть випробування у Logcat:
   * **Крок 1 (Запуск без підписки):** Запустіть додаток, але **НЕ натискайте** кнопку "Підписатися". Подивіться у Logcat. Чи є логи з `ViewModel`? *(Ні, оскільки холодний `Flow` взагалі не виконується без активного споживача!)*.
   * **Крок 2 (Натискання "Підписатися"):** Натисніть "Підписатися". Зверніть увагу: обчислення у `ViewModel` починаються відразу з числа 1, і у логах з'являються повідомлення від `ViewModel` та `Activity`.
   * **Крок 3 (Натискання "Скасувати"):** Натисніть "Скасувати". Що сталося з логами у `ViewModel`? Обчислення у `flow { ... }` **повністю зупинилися**, оскільки кількість підписників стала дорівнювати 0!
   * **Крок 4 (Повторна підписка):** Через кілька секунд натисніть "Підписатися" знову. Зверніть увагу: потік **розпочався з нуля з числа 1**, а не продовжив попередні обчислення!
   * **Крок 5 (Зміна конфігурації / Поворот екрану):** Натисніть "Підписатися" і переверніть екран пристрою або перемкніть систему у Dark Mode. Натисніть "Підписатися" у новій `Activity`. Зверніть увагу: оскільки `Activity` перестворилася, холодний `Flow` **знову скинувся на 1** і почав відлік з початку.

### Експеримент 2: Дослідження Гарячого потоку (`StateFlow`)

1. Модифікуйте `CalculationViewModel`: створіть приватний `_fib = MutableStateFlow(BigInteger.ONE)` та публічний `val fib = _fib.asStateFlow()`.
2. Усередині блоку `init { ... }` класу `ViewModel` запустіть корутину `viewModelScope.launch`, яка безкінечно обчислює числа Фібоначчі і робить `_fib.emit(f1)` кожні `500.milliseconds`.
3. Залишіть кнопки підписки в `MainActivity` без змін.
4. **Проведіть випробування у Logcat:**
   * **Крок 1 (Запуск без підписки):** Запустіть додаток, але **НЕ натискайте** "Підписатися". Подивіться у Logcat. Чи працюють обчислення у `ViewModel`? *(Так! `StateFlow` є гарячим і обчислює числа в RAM незалежно від наявності UI!)*.
   * **Крок 2 (Натискання "Підписатися"):** Натисніть "Підписатися". Зверніть увагу: `Activity` **миттєво отримує поточне накопичене число Фібоначчі**, а не починає з 1.
   * **Крок 3 (Натискання "Скасувати"):** Натисніть "Скасувати". Зверніть увагу: `Activity` перестала отримувати логи, але `ViewModel` **продовжує безперервно рахувати числа у фоні**!
   * **Крок 4 (Повторна підписка):** Через 5 секунд натисніть "Підписатися" знову. Ви відразу отримаєте нове велике число Фібоначчі, яке накопичилося за цей час у `StateFlow`!
   * **Крок 5 (Зміна конфігурації / Поворот екрану):** Натисніть "Підписатися" і переверніть екран кілька разів поспіль. Натисніть "Підписатися" у новій `Activity`. Зверніть увагу: оскільки `CalculationViewModel` переживає поворот екрану, а `StateFlow` зберігає стан у RAM, нова `Activity` **миттєво підключається до актуального обчисленого числа** без скидання на 1 та без створення подвійних обчислень!

## Контрольні запитання для аналізу

За результатами проведених експериментів дайте відповіді на такі запитання:
1. Чому `Flow` називається "холодним" і чому при скасуванні або повороті екрану обчислення Фібоначчі скидалися і починалися з 1?
2. Чому `StateFlow` називається "гарячим" і чому при повторній підписці чи повороті екрану `Activity` відразу отримувала актуальне накопичене число з RAM?
3. Що станеться, якщо натиснути кнопку "Підписатися" двічі поспіль без перевірки `if (fibonacciJob != null)`?
