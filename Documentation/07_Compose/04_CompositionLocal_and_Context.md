# CompositionLocal та робота з Context у Compose

Зазвичай у Jetpack Compose дані передаються "згори донизу" через параметри функцій (цей патерн називається *State Hoisting* — прокидання стану). Але є речі, які потрібні майже всім компонентам дуже глибоко в дереві: налаштування теми (кольори, шрифти), напрям тексту (LTR/RTL) або доступ до системи Android (`Context`).

Якби ми передавали `Context` або колір фону як параметр у кожну функцію (від головного екрану до найменшої кнопки), наш код був би жахливим і важким для підтримки. Для вирішення цієї проблеми розробили механізм **`CompositionLocal`**.

---

## 1. Що таке `CompositionLocal`?

**`CompositionLocal`** — це механізм "неявної передачі" (implicit data passing) даних через дерево Compose. 

Він дозволяє надати (provide) об'єкт десь на самій верхівці дерева, а потім будь-яка дочірня функція глибоко внизу може його "дістати" (read), не приймаючи його через власні параметри.

> 💡 **Приклад з життя:** Саме завдяки цьому механізму працює тема вашого додатку! Коли ви викликаєте `MaterialTheme.colorScheme.primary`, Compose насправді використовує `CompositionLocal`, щоб витягнути кольори, які ви задали нагорі екрану у блоці `MyApplicationTheme { ... }`.

---

## 2. Робота з Android Context (`LocalContext.current`)

**`LocalContext`** — це один із вбудованих об'єктів `CompositionLocal`, який автоматично надається самою платформою Android.

> 💡 **Аналогія з класичним View-підходом:** Якщо ви раніше працювали з XML, ви пам'ятаєте, що будь-який об'єкт типу `View` (наприклад, `Button` чи `TextView`) завжди мав вбудований метод `getContext()`. Оскільки у світі Compose ми працюємо зі звичайними Kotlin-функціями, у них немає жодного вбудованого `getContext()`. Саме `LocalContext.current` є сучасною альтернативою для отримання доступу до `Context`!

### Як працює `LocalContext.current`?
Коли ви викликаєте `val context = LocalContext.current`:
1. Compose дивиться на поточне місце в дереві UI.
2. Піднімається вгору по дереву, поки не знайде найближчий провайдер `LocalContext`.
3. Зазвичай цим провайдером виступає метод `setContent { ... }` у вашій `Activity`. Тому виклик `.current` поверне екземпляр цієї `Activity` (яка і є Android-контекстом).

---

## 3. Золоті правила роботи з Context у Compose

Хоча `LocalContext.current` — це дуже зручний інструмент, використовувати його треба обережно, дотримуючись чотирьох важливих правил:

### Правило 1: Уникайте витоків пам'яті (Memory Leaks)
`LocalContext.current` зазвичай повертає поточну `Activity`. Якщо ви передасте цей контекст в довгоживучий об'єкт (наприклад, у Singleton-клас, у `ViewModel` або запустите тривалу корутину у `GlobalScope`), ви створите витік пам'яті: `Activity` не зможе знищитися системою, коли користувач закриє екран, оскільки на неї посилатиметься ваш об'єкт. 

> ⚠️ **Рішення:** Якщо вам потрібен контекст для `ViewModel` або бази даних (яка живе довше за екран), завжди використовуйте контекст додатку: `context.applicationContext`.

### Правило 2: Не передавайте Context як параметр
Якщо вашій дочірній Composable-функції потрібен контекст (щоб надіслати бродкаст або запустити службу), **не треба приймати його як аргумент**. Він завжди доступний усередині через `LocalContext`!

```kotlin
// ❌ ПОГАНО
@Composable
fun MyButton(context: Context) {
    Button(onClick = { Toast.makeText(context, "Hello", Toast.LENGTH_SHORT).show() }) { ... }
}

// ✅ ДОБРЕ
@Composable
fun MyButton() {
    val context = LocalContext.current // Отримуємо прямо на місці
    Button(onClick = { Toast.makeText(context, "Hello", Toast.LENGTH_SHORT).show() }) { ... }
}
```

### Правило 3: Намагайтеся тримати Context "на краях" системи
Compose-функції мають бути максимально чистими і сфокусованими на UI. Якщо ви можете виконати дію без Context (наприклад, перемістити логіку обчислень у `ViewModel`), зробіть це там. 

`LocalContext` потрібен здебільшого для виклику суто Android-специфічних речей, які ще не мають аналогів у Compose: 
* Показ `Toast`.
* Створення `Intent` (щоб запустити `Service` чи `Activity`).
* Відправка `sendBroadcast`.
*(До речі, для отримання стрінг-ресурсів є спеціальна функція `stringResource(id)`, тому Context для цього викликати не потрібно).*

### Правило 4: Викликати `current` можна ТІЛЬКИ всередині `@Composable`
Ви не можете викликати `LocalContext.current` у звичайній функції, класі або прямо всередині колбека (наприклад, `onClick`), оскільки це не Composable-контекст. 

Значення треба "витягнути" на рівні самої функції `@Composable`, зберегти у змінну, а вже потім використовувати цю змінну всередині лямбда-виразів:

```kotlin
@Composable
fun BadExample() {
    Button(onClick = {
        // ❌ ПОМИЛКА: .current не можна кликати всередині звичайної лямбди onClick!
        val context = LocalContext.current 
        startMyService(context)
    })
}

@Composable
fun GoodExample() {
    // ✅ ПРАВИЛЬНО: Витягуємо Context на рівні Composable-функції
    val context = LocalContext.current 
    
    Button(onClick = {
        // Успішно використовуємо закешовану змінну context всередині onClick
        startMyService(context) 
    })
}
```
