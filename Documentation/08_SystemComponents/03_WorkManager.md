# Гарантоване фонове виконання: WorkManager

У попередньому туторіалі ми дізналися, що для довготривалої роботи у фоні використовується `Foreground Service`. Однак він має серйозний недолік — **він вимагає показу постійного сповіщення**, що дратує користувача.

Що робити, якщо вам потрібно виконати роботу у фоні (наприклад, завантажити логи на сервер, оновити базу даних або щоденно синхронізувати контакти), і вам **не хочеться показувати сповіщення**, а також якщо ви хочете, щоб робота виконалася **гарантовано**, навіть якщо телефон перезавантажиться?

Для цього Google створив бібліотеку **`WorkManager`**.

> 📦 **Початковий проект:** Заготовку проекту для роботи з WorkManager (базовий Compose UI) ви знайдете у репозиторії: [krenevych/Concurrency](https://github.com/krenevych/Concurrency) (гілка **`main`**, модуль **`workmanager`**).\
> 💡 **Приклад розв'язку:** Готовий завершений код із реалізованими `OneTimeWorkRequest` та `PeriodicWorkRequest` знаходиться на гілці **`workmanager_end`** (модуль **`workmanager`**).

---

## 1. Що таке WorkManager?
**WorkManager** — це сучасне рішення Jetpack для **гарантованого** відкладеного виконання фонових задач.

### Головні переваги WorkManager:
* **Гарантія виконання:** Задача гарантовано виконається (навіть якщо користувач закрив додаток через свайп або перезавантажив телефон!).
* **Умови виконання (Constraints):** Ви можете задати специфічні системні умови для запуску задачі (наприклад, "тільки коли підключено Wi-Fi" або "тільки якщо телефон на зарядці"). Це шалено економить батарею користувача.
* **Підтримка Корутин:** Ідеально інтегрований з Kotlin Coroutines через клас `CoroutineWorker`.

### Коли використовувати `WorkManager`?
* Періодична синхронізація (кожні 15 хвилин).
* Завантаження аналітики на сервер уночі.
* Стиснення відео чи завантаження фотографій на сервер у фоні.

## 2. Створення та запуск задачі у WorkManager

### Крок 1. Залежності
Додайте бібліотеку `WorkManager` (з підтримкою Coroutines) у `build.gradle.kts`:
```kotlin
implementation("androidx.work:work-runtime-ktx:2.9.0")
```

### Крок 2. Створення "Робочого класу" (`CoroutineWorker`)
Ви успадковуєтеся від `CoroutineWorker` і перевизначаєте призупиняючу `suspend` функцію **`doWork()`**, яка автоматично виконується у фоновому потоці (`Dispatchers.Default`):

```kotlin
class SyncWorker(
    context: Context,
    workerParams: WorkerParameters
) : CoroutineWorker(context, workerParams) {

    // Цей код гарантовано запуститься ОС Android у фоновому потоці
    override suspend fun doWork(): Result {
        return try {
            Log.d("WorkManager", "Починаємо синхронізацію...")
            
            // Ваш код...
            val response = apiInterface.syncData() 
            
            Log.d("WorkManager", "Синхронізація успішна!")
            
            // Якщо задача виконана успішно
            Result.success() 
            
        } catch (e: Exception) {
            Log.e("WorkManager", "Помилка мережі", e)
            
            // У разі помилки — просимо систему автоматично повторити спробу пізніше!
            Result.retry() 
        }
    }
}
```

### Крок 3. Запуск задачі з Умовами (`Constraints`)

Ви можете запустити задачу лише один раз (`OneTimeWorkRequest`) або повторювати її періодично (`PeriodicWorkRequest`):

```kotlin
// 1. Створюємо умови для запуску (Constraints)
val constraints = Constraints.Builder()
    .setRequiredNetworkType(NetworkType.UNMETERED) // Тільки на Wi-Fi (безлімітний трафік)
    .setRequiresCharging(true)                     // Тільки якщо телефон на зарядці
    .build()

// 2. Створюємо запит на виконання нашої задачі
val syncRequest = OneTimeWorkRequestBuilder<SyncWorker>()
    .setConstraints(constraints) // Додаємо умови
    .build()

// 3. Ставимо задачу у системну чергу WorkManager
WorkManager.getInstance(context).enqueue(syncRequest)
```

> 💡 **Як це працює під капотом?**
> Ви ставите задачу в чергу і забуваєте про неї. Система Android сама відстежує стан смартфона. Вона дочекається моменту, коли користувач підключить телефон до зарядки та увійде у зону Wi-Fi (навіть уночі!), і тільки тоді "розбудить" ваш додаток та запустить метод `doWork()`!

#### Популярні умови запуску (Constraints):
Умови `Constraints` — це найпотужніша фішка WorkManager. Ви можете комбінувати кілька умов, і Android запустить вашу задачу **ТІЛЬКИ тоді, коли всі ці умови будуть виконані одночасно**.

| Метод `Builder` | Значення / Опис умови |
| :--- | :--- |
| **`setRequiredNetworkType`** | Вимагає наявності інтернету.<br>• `NetworkType.CONNECTED` (будь-який інтернет)<br>• `NetworkType.UNMETERED` (лише безлімітний, тобто Wi-Fi) |
| **`setRequiresCharging`** | `true` — задача запуститься тільки коли телефон підключено до зарядного пристрою. |
| **`setRequiresBatteryNotLow`** | `true` — задача не запуститься, якщо телефон перебуває у режимі критично низького заряду (Low Battery). |
| **`setRequiresDeviceIdle`** | `true` — задача запуститься тільки коли телефон лежить на столі без активного використання (спить). (Доступно з API 23). |
| **`setRequiresStorageNotLow`** | `true` — задача не запуститься, якщо на пристрої критично мало вільного місця. |

## 3. Періодичні задачі (`PeriodicWorkRequest`)

Якщо вам потрібно, щоб задача виконувалася не одноразово, а регулярно (наприклад, щоденна синхронізація з сервером), використовується `PeriodicWorkRequest`. 

```kotlin
// Створюємо періодичну задачу: виконувати кожні 12 годин
val periodicSyncRequest = PeriodicWorkRequestBuilder<SyncWorker>(
    repeatInterval = 12, 
    repeatIntervalTimeUnit = TimeUnit.HOURS
)
    .setConstraints(constraints) // Умови залишаються такими самими
    .build()
```

#### Доступні одиниці часу (`TimeUnit`):
| Значення `TimeUnit` | Опис | Мінімальний ліміт в Android |
| :--- | :--- | :--- |
| **`TimeUnit.DAYS`** | Дні | 1 день |
| **`TimeUnit.HOURS`** | Години | 1 година |
| **`TimeUnit.MINUTES`** | Хвилини | **Мінімум 15 хвилин** |
| **`TimeUnit.SECONDS`** | Секунди | *Не рекомендується* (Мінімум 900 секунд) |
| **`TimeUnit.MILLISECONDS`** | Мілісекунди | *Не рекомендується* (Мінімум 900 000 мс) |

> ⚠️ **Важливе обмеження:** Мінімальний дозволений інтервал для періодичних задач в Android становить **15 хвилин**. Ви не можете налаштувати WorkManager на виконання кожні 5 чи 10 хвилин.

---

### Чому використовується `enqueueUniquePeriodicWork`?

Якби ви використали стандартний метод `enqueue()`, то при кожному відкритті екрану створювалася б **нова, додаткова копія** вашої щоденної задачі. За тиждень у користувача в тлі працювало б 100 однакових задач синхронізації, що вбило б батарею!

Щоб уникнути дублювання, використовують **`enqueueUniquePeriodicWork`**. Цей метод перевіряє, чи не запущена вже задача з таким самим ім'ям:

```kotlin
WorkManager.getInstance(context).enqueueUniquePeriodicWork(
    "daily_sync", // Унікальне ім'я задачі
    ExistingPeriodicWorkPolicy.KEEP, // Політика вирішення конфліктів
    periodicSyncRequest
)
```

#### Політики вирішення конфліктів (`ExistingPeriodicWorkPolicy`):
| Політика | Поведінка системи, якщо задача з ім'ям "daily_sync" вже існує |
| :--- | :--- |
| **`KEEP`** | **(Найпопулярніша)** Ігнорує новий запит і дозволяє існуючій задачі продовжувати працювати за її старим графіком. |
| **`REPLACE`** | Зупиняє і видаляє стару задачу, замінюючи її на нову. Зручно, якщо змінилися параметри `Constraints` або налаштування. |
| **`UPDATE`** | М'яко оновлює налаштування поточної задачі, не перериваючи її поточного виконання. |

## 4. Як передавати та отримувати дані з WorkManager?

### 1. Передача даних у задачу (Input Data)
Дані передаються через об'єкт `Data`. Ви додаєте їх до запиту за допомогою `setInputData`:

```kotlin
val inputData = Data.Builder()
    .putString("server_url", "https://api.example.com/sync")
    .build()

val syncRequest = OneTimeWorkRequestBuilder<SyncWorker>()
    .setInputData(inputData) // Передаємо дані у Воркер
    .build()
```

Усередині `doWork()` ви зчитуєте ці дані:
```kotlin
override suspend fun doWork(): Result {
    // Зчитуємо переданий рядок
    val url = inputData.getString("server_url") ?: return Result.failure()
    // ...
}
```

### 2. Відстеження статусу та отримання результату (Output Data)
Оскільки WorkManager працює у фоні, вашому UI (екрану чи `ViewModel`) потрібно якось дізнаватися, що відбувається із задачею. Ви можете **підписатися на системний об'єкт `WorkInfo`**, який містить поточний стан задачі (`State`) та передані результати виконання (`outputData`).

Щоб відстежувати цей `WorkInfo` в реальному часі, використовуйте метод `getWorkInfoByIdLiveData(...)`:

```kotlin
// 1. У класі SyncWorker повертаємо результат після успішного виконання:
val outputData = Data.Builder().putString("status", "Успішно завантажено!").build()
return Result.success(outputData)


// 2. В Activity (або ViewModel) підписуємося на зміни статусу задачі:
WorkManager.getInstance(context)
    .getWorkInfoByIdLiveData(syncRequest.id) // Підписка за унікальним ID задачі
    .observe(this) { workInfo ->
        // Перевіряємо, чи задача успішно закінчилася
        if (workInfo != null && workInfo.state == WorkInfo.State.SUCCEEDED) {
            // Тільки у стані SUCCEEDED ми можемо витягнути фінальний результат!
            val message = workInfo.outputData.getString("status")
            Log.d("App", "Готово: $message")
        }
    }
```

### 3. Життєвий цикл задачі (`WorkInfo.State`)

Коли ви викликаєте `enqueue()`, задача не виконується миттєво. Вона проходить такий життєвий цикл станів (`State`):

| Стан (`WorkInfo.State`) | Тип | Опис та поведінка |
| :--- | :--- | :--- |
| **`ENQUEUED`** (В черзі) | Тимчасовий | Відразу після `enqueue()` задача отримує цей стан. У ньому вона може перебувати годинами, чекаючи, поки виконаються жорсткі умови (наприклад, з'явиться Wi-Fi). Якщо `doWork()` поверне `Result.retry()`, задача теж повернеться сюди. |
| **`RUNNING`** (Виконується) | Тимчасовий | Щойно всі умови виконано, система переводить її у цей стан і запускає ваш метод `doWork()`. |
| **`SUCCEEDED`** (Успішно) | **Термінальний** | Якщо `doWork()` повертає `Result.success()`, задача завершується. Лише в цьому стані стають доступними дані з `outputData`. |
| **`FAILED`** (Помилка) | **Термінальний** | Виникає, якщо `doWork()` повертає `Result.failure()` (означає остаточний провал без повторних спроб). |
| **`CANCELLED`** (Скасовано) | **Термінальний** | Виникає, якщо ви вручну скасовуєте задачу (наприклад, через `cancelWorkById()`). |
| **`BLOCKED`** (Заблоковано) | Тимчасовий | Використовується рідко — лише коли ваша задача є частиною ланцюжка (Chained Work) і змушена чекати успішного завершення попередньої задачі. |

#### Приклад відстеження всіх станів життєвого циклу:
Ви можете реагувати на будь-які зміни стану задачі прямо у вашому UI (наприклад, щоб показувати спінер під час `RUNNING` або повідомлення про помилку під час `FAILED`):

```kotlin
WorkManager.getInstance(context)
    .getWorkInfoByIdLiveData(syncRequest.id)
    .observe(this) { workInfo ->
        if (workInfo != null) {
            when (workInfo.state) {
                WorkInfo.State.ENQUEUED -> Log.d("App", "Задача у черзі (очікує умов)")
                WorkInfo.State.RUNNING -> Log.d("App", "Задача виконується прямо зараз!")
                WorkInfo.State.SUCCEEDED -> Log.d("App", "Задача успішно завершилася!")
                WorkInfo.State.FAILED -> Log.e("App", "Задача впала з помилкою (і не має retry)!")
                WorkInfo.State.CANCELLED -> Log.d("App", "Задачу скасовано вручну.")
                WorkInfo.State.BLOCKED -> Log.d("App", "Задача заблокована іншою задачею у ланцюжку.")
            }
        }
    }
```

## 5. Порівняння: Що та коли обрати?

Щоб не помилитися з вибором технології для фонової роботи, запам'ятайте цю шпаргалку:

| Інструмент | Опис | Коли використовувати? |
| :--- | :--- | :--- |
| **`Coroutines`** (`viewModelScope`) | Звичайні асинхронні задачі. Вмирають разом з екраном або при згортанні додатка. | Завантаження даних для відображення на екрані (поки юзер дивиться на екран). |
| **`Bound Service`** | Служба-сервер без сповіщення. Живе, поки до неї прив'язаний хоча б один клієнт. | Для взаємодії між компонентами (плеєр, Bluetooth-зв'язок). Зазвичай комбінується з Foreground Service. |
| **`Foreground Service`** | Безперервна служба з обов'язковим сповіщенням. Працює поки згорнуто додаток. | Музичний плеєр, таймер бігу, завантаження великого фільму, дзвінок. |
| **`WorkManager`** | Гарантоване відкладене виконання задач системою. Без сповіщень. | Синхронізація бази даних вночі на Wi-Fi, відправка аналітики чи бекапів. |

---

## Підсумок

* **`WorkManager`** — інструмент для гарантованих, відкладених у часі фонових задач.
* Задачі формулюються через клас **`CoroutineWorker`** та його призупиняючий метод **`doWork()`**, який автоматично працює у фоні.
* Метод `doWork()` повинен повернути стан: `Result.success()`, `Result.failure()` або `Result.retry()` (для автоматичного повторного запуску).
* Завдяки **`Constraints`** можна задати умови: "тільки Wi-Fi" (`UNMETERED`) або "тільки на зарядці" (`setRequiresCharging`), зберігаючи акумулятор користувача.
