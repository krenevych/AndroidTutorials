# Системні компоненти: Служби (Services)

Служби використовуються для виконання **тривалих фонових операцій**, які повинні продовжувати працювати навіть тоді, коли користувач згорнув додаток або перейшов на інший екран (наприклад: відтворення музики, завантаження великих файлів або відстеження GPS).

---

## 1. Що таке `Service`?

`Service` — це системний компонент, який працює у фоновому режимі без графічного інтерфейсу (UI). Його головна задача — виконувати роботу, коли користувач не взаємодіє з додатком напряму.

Разом з `Activity`, `BroadcastReceiver` та `ContentProvider`, **`Service` (Служба)** є одним із 4-х фундаментальних компонентів Android.

> 💡 Такі застосунки, як антивіруси, системні утиліти, фонові клавіатури чи модулі безпеки, можуть **взагалі не мати візуальної частини (жодної `Activity`)**. Уся їхня робота та бізнес-логіка повністю будуються виключно на комбінації фундаментальних компонентів системи: `Service` та `BroadcastReceiver`.

### ❓ Чому просто не використати Корутину або Thread?
У початківців часто виникає питання: навіщо створювати цілий системний компонент `Service`, якщо можна просто запустити фонову корутину (наприклад, `CoroutineScope.launch`)?

Відповідь полягає у **керуванні пам'яттю операційної системи Android**:
* Якщо ви запустите звичайний потік або корутину і користувач згорне додаток, система Android може будь-якої миті "вбити" ваш процес для звільнення оперативної пам'яті (і ваша корутина просто обірветься).
* Коли ви запускаєте **`Service`**, ви офіційно повідомляєте операційній системі: *"Мій додаток зараз виконує важливу фонову роботу. Будь ласка, підвищ пріоритет мого процесу і не вбивай його"*.

> ⚠️ **Критичне правило Service:**
> Як і `BroadcastReceiver` чи `Activity`, звичайний **Service за замовчуванням виконується у Головному потоці (Main Thread)**! Якщо ваша служба має робити важкі обчислення або завантаження, вона повинна самостійно запускати Корутини чи фонові потоки всередині себе (`onStartCommand` має відпрацювати миттєво). В іншому випадку служба заблокує UI вашого додатка (ANR).

### Обов'язкова реєстрація в `AndroidManifest.xml`
Як і будь-який інший фундаментальний компонент системи (наприклад, `Activity` чи `BroadcastReceiver`), кожен створений вами клас служби **обов'язково має бути зареєстрований у файлі маніфесту** `AndroidManifest.xml` усередині тегу `<application>`. Без цієї реєстрації система Android не знатиме про існування вашої служби і викине краш при спробі її запуску.

```xml
<manifest ...>
    <application ...>
        <!-- Реєстрація служби у маніфесті -->
        <service android:name=".MyBackgroundService" />
    </application>
</manifest>
```

### Основні методи життєвого циклу Служби
Подібно до `Activity`, служба має свій життєвий цикл:
* **`onCreate()`** — викликається лише один раз при першому створенні служби. Використовується для одноразового налаштування (наприклад, ініціалізації плеєра).
* **`onStartCommand()`** — викликається щоразу, коли інший компонент (наприклад, `Activity`) просить запустити службу через `startService()`. Саме тут стартує ваша головна робота. 
* **`onDestroy()`** — викликається при знищенні служби (після виклику `stopSelf()` зсередини або `stopService()` ззовні). Тут необхідно скасувати корутини та звільнити ресурси.

### `Service` є повноцінним Context
Важлива архітектурна деталь: клас `Service` напряму успадковується від класу `ContextWrapper` (так само як і `Activity` або `Application`). 

Це означає, що **усередині служби ви завжди маєте прямий доступ до `Context`** просто звертаючись до `this`. Ви можете легко запускати інші наміри (`Intent`), розсилати бродкасти (`sendBroadcast()`), отримувати доступ до бази даних або ресурсів.

> ⚠️ **Різниця між `Service Context` та `Activity Context`:**
> Хоча `Service` є контекстом, **це НЕ візуальний контекст**. Він не містить жодної інформації про UI-тему (Theme), метрики екрану чи вбудовані вікна. Тому ви **не можете** використовувати `Service Context` для показу діалогових вікон (`AlertDialog`), роздування макетів (`LayoutInflater`) чи роботи з UI-елементами. За спробу зробити це Android викине помилку!

## 2. Типи Служб

В Android служби поділяються на 3 головні типи, кожен з яких має своє специфічне призначення та обмеження.

### 1. Фонова служба (Background Service)
Це найстаріший тип служби. Виконує роботу, яку користувач фізично не бачить (наприклад, стиснення фотографій або перевірка нових повідомлень). 

* **Приклади використання:** Синхронізація контактів з сервером, періодична перевірка нових повідомлень, завантаження аналітики у фон.
* **Життєвий цикл:** Запускається викликом `startService(intent)`. Працює самостійно у фоні. Щоб її зупинити, служба повинна викликати `stopSelf()` зсередини, або інший компонент має викликати `stopService()` ззовні.
* **Особливості (Жорсткі обмеження Android 8.0+):** Якщо користувач згорне додаток, система почекає пару хвилин і **автоматично вб'є всі фонові служби** для економії заряду батареї. Тому сьогодні для таких задач використовують виключно `WorkManager`!

---

### 2. Прив'язана служба (Bound Service)
Це служба, яка діє як "сервер" в архітектурі клієнт-сервер.

* **Приклади використання:** Коли потрібна двостороння взаємодія. Наприклад, `Activity` отримує об'єкт `IBinder` музичного плеєра і може викликати його публічні методи: `musicService.play()`, `musicService.pause()`, `musicService.getCurrentTime()`.
* **Життєвий цикл:** Замість команди `startService()`, компонент (наприклад, `Activity`) "прив'язується" до служби за допомогою команди `bindService()`.
  Служба живе рівно стільки, скільки до неї прив'язаний хоча б один клієнт. Коли остання `Activity` викликає `unbindService()`, служба автоматично знищується.
* **Особливості:** Не працює самостійно у фоні без клієнта. Проте одна і та сама служба може бути **Гібридною** (одночасно запущеною через `startService` та прив'язаною через `bindService`), що дозволяє їй працювати у фоні та приймати клієнтів.

---

### 3. Активна служба (Foreground Service)
Служба, яка виконує операції, про які користувач **обов'язково повинен знати і бачити їхній хід**. 

* **Приклади використання:** Відтворення музики у плеєрі, запис GPS-треку під час бігу, активний телефонний дзвінок, скачування великого файлу, трансляція екрану (Screen Mirroring).
* **Життєвий цикл:** Запускається через `startForegroundService()` і **зобов'язана** перевести себе у стан Foreground викликом `startForeground(id, notification)`. Працює безстроково, доки сама не викличе `stopSelf()` або не отримає команду `stopService()` ззовні.
* **Особливості:** Оскільки служба інформує користувача про свою роботу через постійне (Non-dismissible) сповіщення у статус-барі, операційна система Android вважає її критично важливою і **НЕ вбиває**, навіть коли додаток згорнуто.

### ❓ Хто запускає Службу, якщо у застосунку немає `Activity`?
Як ми зазначали у першому розділі, існують застосунки без візуальної частини. Якщо користувач не може натиснути на іконку додатка, початковий поштовх для запуску його Служби дають інші компоненти системи:
1. **Через `BroadcastReceiver`:** Додаток реєструє в маніфесті системну подію (наприклад, `ACTION_BOOT_COMPLETED` при увімкненні телефону). Приймач ловить цю подію і викликає `context.startForegroundService(...)` зсередини методу `onReceive()`.
2. **Через інший додаток (Bound Service):** Ваш додаток працює як провайдер логіки. Інший додаток на телефоні викликає `bindService()` до вашого пакету, і система автоматично "будить" вашу службу.

> ⚠️ **Важливий нюанс безпеки:** Після встановлення додатка система тримає його у стані **"Stopped"**. Жодні системні бродкасти чи служби не запрацюють, поки користувач не запустить додаток **хоча б один раз вручну**. Саме тому сучасні "безликі" утиліти зазвичай мають хоча б одну мінімальну `Activity` для першого кліку, надання базових дозволів та первинного запуску `Service`.

## 3. Foreground Service

У сучасному Android `ForegroundService` — це єдиний надійний спосіб виконати **безперервну фонову роботу в реальному часі** (наприклад, відтворення музики, трекінг GPS чи таймер бігу), яку система **не має права відкладати чи переривати**, поки додаток згорнуто у фон.

*(Примітка: для відкладених задач, які не потребують негайного виконання в реальному часі, використовується `WorkManager`, про який ми поговоримо у наступному розділі).*

### Крок 1. Декларація сервісу у `AndroidManifest.xml` та дозволи

Починаючи з Android 14+ (API 34 та вище) система вимагає декларувати **конкретний тип служби** (наприклад, відтворення медіа, синхронізація чи завантаження даних).

```xml
        <service
            android:name=".MyForegroundService"
            android:foregroundServiceType="X" />
```

Крім цього, запуск Foreground Service жорстко контролюється трьома рівнями дозволів:

 1. **Базовий дозвіл:** Завжди потрібен загальний дозвіл `FOREGROUND_SERVICE`.

 2. **Специфічний дозвіл типу:** Кожен вказаний вами тип (`foregroundServiceType="X"`) у тегу `<service>` жорстко вимагає наявності відповідного специфічного дозволу `FOREGROUND_SERVICE_X` у маніфесті (вони мають завжди йти в парі). 

 3. **Дозвіл на саму функцію:** Для "небезпечних" типів (наприклад, `location` чи `camera`) система додатково перевірить, чи має додаток звичайні дозволи на доступ до цієї функції (наприклад, `ACCESS_COARSE_LOCATION` чи `CAMERA`).
>
> *Якщо хоча б один із цих дозволів не буде вказаний, додаток негайно впаде з помилкою `SecurityException`!*

#### Приклад для звичайної служби (один тип):
```xml
<manifest ...>
    <!-- 1. Базовий дозвіл -->
    <uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
    
    <!-- 2. Специфічний дозвіл для типу dataSync -->
    <uses-permission android:name="android.permission.FOREGROUND_SERVICE_DATA_SYNC" />

    <application>
        <!-- Вказуємо тип служби -->
        <service
            android:name=".DownloadService"
            android:foregroundServiceType="dataSync" />
    </application>
</manifest>
```

> 💡 Одна служба може мати **декілька типів одночасно**. У такому випадку типи розділяються символом `|` (наприклад, `mediaPlayback|location`). 
> Також необхідно додати в маніфест **усі дозволи, які вимагаються кожним із вказаних типів**.

#### Приклад для комбінованої служби (декілька типів + дозвіл на функцію):
```xml
<manifest ...>
    <!-- 1. Базовий дозвіл -->
    <uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
    
    <!-- 2. Специфічні дозволи для обох типів -->
    <uses-permission android:name="android.permission.FOREGROUND_SERVICE_MEDIA_PLAYBACK" />
    <uses-permission android:name="android.permission.FOREGROUND_SERVICE_LOCATION" />

    <!-- 3. Звичайний дозвіл на доступ до функції (оскільки використовується тип location) -->
    <uses-permission android:name="android.permission.ACCESS_COARSE_LOCATION" />

    <application>
        <!-- Вказуємо обидва типи через символ '|' -->
        <service
            android:name=".RunningTrackerService"
            android:foregroundServiceType="mediaPlayback|location" />
    </application>
</manifest>
```

#### Популярні типи `foregroundServiceType` в Android 14+ (API 34):

| Тип (`foregroundServiceType`) | Для чого використовується? | Специфічний дозвіл на Foreground | Дозвіл на функцію (Required Permissions) |
| :--- | :--- | :--- | :--- |
| **`mediaPlayback`** | Музичні та відеоплеєри. | `FOREGROUND_SERVICE_MEDIA_PLAYBACK` | — |
| **`location`** | Навігація, трекінг бігу, відстеження GPS у реальному часі. | `FOREGROUND_SERVICE_LOCATION` | `ACCESS_COARSE_LOCATION` або `ACCESS_FINE_LOCATION` |
| **`dataSync`** | Завантаження, вивантаження великих файлів чи бекап баз даних. | `FOREGROUND_SERVICE_DATA_SYNC` | — |
| **`phoneCall`** | VoIP застосунки, відеодзвінки (Telegram, WhatsApp). | `FOREGROUND_SERVICE_PHONE_CALL` | `MANAGE_OWN_CALLS` |
| **`camera`** | Запис відео чи робота з камерою у фоні. | `FOREGROUND_SERVICE_CAMERA` | `CAMERA` |
| **`microphone`** | Фоновий запис голосу або диктофон. | `FOREGROUND_SERVICE_MICROPHONE` | `RECORD_AUDIO` |
| **`connectedDevice`** | Зв'язок із Bluetooth-пристроями (годинники, фітнес-браслети). | `FOREGROUND_SERVICE_CONNECTED_DEVICE` | `BLUETOOTH_CONNECT` або інші BT-дозволи |
| **`specialUse`** | Усі інші унікальні випадки, які не підпадають під категорії вище. | `FOREGROUND_SERVICE_SPECIAL_USE` | — |

> 🚨 **Неочевидний підводний камінь — Невидиме сповіщення (Android 13+):** 
> Починаючи з Android 13 (API 33), для показу будь-яких сповіщень додатки зобов'язані запитувати у користувача runtime-дозвіл **`android.permission.POST_NOTIFICATIONS`**. Якщо ви не маєте цього дозволу, ваша Foreground-служба успішно запуститься і працюватиме, але саме сповіщення буде "проковтнуте" системою і не з'явиться у статус-барі!

### Крок 2. Створення класу Служби

Служба має обов'язково створити `Notification` (Сповіщення) та викликати метод `startForeground()` протягом 5 секунд після старту, інакше система її вб'є:

```kotlin
class DownloadService : Service() {

    // Прив'язана служба (Bound) нам не потрібна, тому повертаємо null
    override fun onBind(intent: Intent?): IBinder? = null

    // Викликається лише один раз при створенні служби
    override fun onCreate() {
        super.onCreate()
        // Обов'язково створюємо канал перед створенням сповіщення!
        createNotificationChannel() 
    }

    // Викликається щоразу при старті служби через startForegroundService
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        
        // 1. Створюємо сповіщення
        val notification = createNotification()
        
        // 2. Оголошуємо систему, що ми є Foreground Service! (ID має бути > 0)
        startForeground(1, notification)

        // 3. Запускаємо нашу фонову роботу (Корутину)
        startDownloading()

        return START_NOT_STICKY // Служба не перезапуститься автоматично у разі крашу
    }

    private fun createNotificationChannel() {
        // Канали обов'язкові починаючи з Android 8.0 (API 26)
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O) {
            val channelId = "download_channel"
            val channelName = "Фонове завантаження"
            val channel = NotificationChannel(
                channelId,
                channelName,
                NotificationManager.IMPORTANCE_LOW // Низький пріоритет (без звукового сигналу)
            )
            val manager = getSystemService(NOTIFICATION_SERVICE) as NotificationManager
            manager.createNotificationChannel(channel)
        }
    }

    private fun createNotification(): Notification {
        val channelId = "download_channel"
        
        return NotificationCompat.Builder(this, channelId)
            .setContentTitle("Завантаження файлу")
            .setContentText("Файл завантажується у фоні...")
            // Обов'язкова іконка (зазвичай прозора SVG/XML з папки drawable)
            .setSmallIcon(R.drawable.ic_launcher_foreground) 
            .build()
    }
    
    private fun startDownloading() {
        // ... Логіка завантаження через Coroutines (scope.launch) ...
        // Коли завантаження завершено, викликаємо stopSelf()
    }
}
```

> 💡 **Що таке `NotificationChannel` і навіщо він потрібен?**
> Починаючи з Android 8.0 (API 26), Google заборонив надсилати будь-які сповіщення без вказівки Каналу (Channel). 
> Канали були створені для користувачів: тепер у налаштуваннях телефона користувач бачить не один загальний вимикач "Вимкнути всі сповіщення", а список категорій. Наприклад, він може повністю вимкнути звуки для каналу "Фонове завантаження", але залишити звук для каналу "Особисті повідомлення". Якщо ви спробуєте надіслати `Notification` без прив'язки до зареєстрованого каналу, додаток просто впаде.
>
> У нашому прикладі рядок **`val channelId = "download_channel"`** — це унікальний текстовий ідентифікатор-зв'язка. Ми створюємо системний канал із цим ID у методі `createNotificationChannel()`, а потім прив'язуємо наше конкретне сповіщення до цього ж ID у `NotificationCompat.Builder(this, channelId)`.

### Крок 3. Запуск служби з Activity / ViewModel
Запуск Foreground Service також змінився. Потрібно використовувати **`ContextCompat.startForegroundService()`**:

```kotlin
val serviceIntent = Intent(context, DownloadService::class.java)
ContextCompat.startForegroundService(context, serviceIntent)
```

## 4. Bound Service

Якщо `Foreground Service` працює як самостійний робітник, якому ви дали команду "Старт" і забули, то **`Bound Service`** працює як сервер. До нього можна підключитися (прив'язатися) з `Activity`, щоб **викликати його методи, передавати дані в реальному часі та отримувати результати**.

Ідеальний приклад — музичний плеєр. `Activity` повинна мати можливість викликати у служби методи `play()`, `pause()`, `skipToNext()` та отримувати поточний час треку.

### 🔄 Специфічний життєвий цикл Bound Service
На відміну від звичайного сервісу (де головним є `onStartCommand()`), у `Bound Service` працюють інші методи життєвого циклу:

* **`onBind(intent: Intent)`** — обов'язковий метод. Викликається системою, коли перший клієнт робить `bindService()`. Саме тут ви маєте повернути об'єкт `IBinder`, через який клієнт буде спілкуватися зі службою. *(Важливо: `onStartCommand()` тут **НЕ викликається**).*
* **`onUnbind(intent: Intent)`** — викликається, коли всі клієнти відв'язалися (через `unbindService()`).
* **`onRebind(intent: Intent)`** — (рідковживаний) викликається, якщо новий клієнт прив'язується до служби після того, як спрацював `onUnbind()`, але служба ще не була знищена.

> 💡 **Правило смерті Bound Service:** Служба живе рівно стільки, скільки до неї прив'язаний хоча б один клієнт. Коли остання `Activity` відв'язується, система автоматично викликає `onUnbind()`, а за ним відразу `onDestroy()`, повністю знищуючи службу.
> *(Виняток — "Гібридна служба", яка була одночасно запущена і через `startService`, і через `bindService`. Вона не помре, доки не отримає команду `stopSelf()`).*

### Механізм `LocalBinder`

Щоб налаштувати взаємодію в межах одного додатка, найчастіше використовується механізм **`LocalBinder`**.

#### Крок 1. Створення служби з LocalBinder

Усередині класу служби необхідно створити внутрішній клас, який успадковується від `Binder`. Його єдина мета — повернути екземпляр самої служби клієнту (`Activity`). 

Після цього ми повертаємо цей `Binder` у методі `onBind`:

```kotlin
class MusicPlayerService : Service() {

    // 1. Створюємо наш Binder (Посередник)
    inner class LocalBinder : Binder() {
        // Метод, який поверне саму службу для доступу до її методів
        fun getService(): MusicPlayerService = this@MusicPlayerService
    }

    private val binder = LocalBinder()

    // 2. Цей метод викликається, коли Activity викликає bindService()
    override fun onBind(intent: Intent?): IBinder {
        return binder
    }

    // -----------------------------------------------------
    // Публічні методи служби, які буде викликати Activity
    // -----------------------------------------------------
    
    fun playMusic() {
        Log.d("MusicService", "Музика грає...")
        // Логіка MediaPlayer
    }

    fun pauseMusic() {
        Log.d("MusicService", "Музика на паузі")
    }

    fun getCurrentProgress(): Int {
        return 42 // Заглушка (повертає відсоток або секунди)
    }
}
```

### Крок 2. Прив'язка служби до Activity (`ServiceConnection`)

Щоб `Activity` могла підключитися до служби, їй потрібен об'єкт **`ServiceConnection`**, який слухатиме момент підключення або непередбачуваного розриву зв'язку.

* Прив'язка (`bindService`) зазвичай відбувається у **`onStart()`**.
* Відв'язка (`unbindService`) — у **`onStop()`** (щоб не тримати службу живою, коли екран згорнуто).

```kotlin
class MainActivity : AppCompatActivity() {

    // Посилання на нашу службу
    private var musicService: MusicPlayerService? = null
    private var isBound = false

    // Слухач з'єднання зі службою
    private val connection = object : ServiceConnection {
        override fun onServiceConnected(name: ComponentName?, service: IBinder?) {
            // Отримуємо Binder і витягуємо з нього нашу службу!
            val binder = service as MusicPlayerService.LocalBinder
            musicService = binder.getService()
            isBound = true
            Log.d("App", "Службу підключено!")
        }

        override fun onServiceDisconnected(name: ComponentName?) {
            musicService = null
            isBound = false
        }
    }

    override fun onStart() {
        super.onStart()
        // Створюємо Intent і прив'язуємося до служби
        val intent = Intent(this, MusicPlayerService::class.java)
        // BIND_AUTO_CREATE означає: якщо служба ще не запущена — створи її!
        bindService(intent, connection, Context.BIND_AUTO_CREATE)
    }

    override fun onStop() {
        super.onStop()
        // Обов'язково відв'язуємося, щоб не було витоку пам'яті
        if (isBound) {
            unbindService(connection)
            isBound = false
        }
    }

    // -----------------------------------------------------
    // Виклик методів служби по кліку на кнопки UI
    // -----------------------------------------------------
    private fun onPlayClicked() {
        if (isBound) {
            musicService?.playMusic() // Прямий виклик методу!
        }
    }
}
```

> 💡 **Примітка:** Одна і та сама служба може бути одночасно запущеною через `startService` та прив'язаною через `bindService`.
> Якщо служба запущена **тільки** через `bindService()` (без виклику `startService()`), вона буде автоматично знищена системою (викличеться `onDestroy()`) тієї ж миті, коли остання `Activity` викличе `unbindService()`.

## Підсумок

* **`Service`** — це системний компонент без UI, який використовується для тривалої фонової роботи. Працює у Main Thread.
* Звичайні **Background Services** майже не використовуються через агресивні ліміти батареї в Android 8+.
* **`Foreground Service`** — єдиний надійний спосіб виконати роботу, яку видно користувачу (плеєр, таймер, завантаження). Вона вимагає постійного сповіщення у статус-барі (`startForeground`).
* Починаючи з Android 14 (API 34), обов'язково декларувати специфічний тип `foregroundServiceType` у `AndroidManifest.xml`.
