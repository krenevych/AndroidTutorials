# Скасування та Обробка помилок у Корутинах

При розробці Android-застосунків асинхронні задачі часто потрібно скасовувати (наприклад, при повороті екрану чи закритті Activity) або обробляти помилки мережі й баз даних.

У цьому уроці ми спочатку розглянемо **механізм скасування корутин**, а потім — **способи обробки помилок (Exception Handling)**.

---

## 1. Скасування корутин та Кооперативне скасування

Скасування асинхронних задач — одна з найважливіших дій у мобільній розробці. Якщо користувач згортає чи закриває екран (`onDestroy()`), усі фонові корутини мають миттєво зупинятися, щоб не витрачати акумулятор та оперативну пам'ять.

Скасування корутин здійснюється за допомогою методу **`cancel()`**, який може застосовуватися як до окремої роботи (`Job`), так і до всього об'єкта `CoroutineScope`.

### Схематичні приклади використання `cancel()`:

#### 1. Скасування окремої корутини (`job.cancel()`):
```kotlin
// Запускаємо корутину і зберігаємо посилання на її Job
val downloadJob: Job = scope.launch {
    downloadFile()
}

// Скасовуємо ТІЛЬКИ цю конкретну задачу (наприклад, користувач натиснув "Скасувати завантаження")
downloadJob.cancel()
```

#### 2. Скасування всього Scope (`scope.cancel()`):
```kotlin
val scope = CoroutineScope(Dispatchers.Main)

scope.launch { task1() }
scope.launch { task2() }

// Остаточно знищуємо ВЕСЬ Scope і зупиняємо ВСІ корутини у ньому (наприклад, у onDestroy)
scope.cancel()
// УВАГА: Після цього scope стає "мертвим", нові корутини в ньому запустити неможливо!
```

> 🔴 **Пастка для розробників: Запам'ятайте різницю!**
> 
> * **`scope.cancel()`** — знищує область видимості корутин **назавжди**. Спроба викликати `scope.launch { ... }` у скасованому Scope буде мовчки ігноруватися — нова корутина скасується ще до старту. Викликайте `scope.cancel()` **тільки при остаточному закритті екрану** (`onDestroy()` чи `onCleared()`).
> * **`job.cancel()`** — зупиняє **тільки одну конкретну задачу**. Сам `CoroutineScope` залишається повністю активним для наступних запусків.
> 
> 💡 **Золоте правило:** Для скасування попередньої дії при повторній команді користувача (наприклад, при перезапуску таймера чи повторному кліку кнопки) — зберігайте `Job` і викликайте **`job?.cancel()`**, але **ніколи не викликайте `scope.cancel()`**!

---

### Принцип Кооперативного скасування (Cooperative Cancellation)

Скасування в Kotlin є **кооперативним (Cooperative)**. Це означає, що система не може насильно вбити або перервати корутину посеред виконання її коду (на відміну від застарілого й небезпечного `Thread.stop()` у Java).

> ⚠️ **Корутина повинна СAMA перевіряти, чи її не скасували!**

#### Як працює автоматична перевірка:
Усі стандартні призупиняючі (`suspend`) функції з бібліотеки `kotlinx.coroutines` (такі як `delay()`, `withContext()`, `await()`, `yield()`) **автоматично перевіряють статус скасування** перед кожною своєю дією. Якщо корутину було скасовано, вони викидають спеціальний виняток **`CancellationException`**, який зупиняє виконання корутини.

---

### Проблема з обчислювальними циклами (Без кооперації)

Якщо у вашому коді виконується звичайний обчислювальний цикл `for` або `while` без виклику інших `suspend` функцій, цей цикл **НЕ ЗУПИНИТЬСЯ** сам по собі, навіть якщо ви викличете `job.cancel()`!

#### ❌ Приклад ПОМИЛКИ (Корутина ігнорує скасування):
```kotlin
val job = lifecycleScope.launch(Dispatchers.Default) {
    var count = 0
    // Важкий обчислювальний цикл на 100 мільйонів ітерацій
    for (i in 1..100_000_000) {
        count += i
    }
    // Навіть якщо викликати job.cancel(), цей цикл НЕ зупиниться і крутитиметься до кінця!
    Log.d(TAG, "Завершено обчислення: $count")
}

// У разі виходу з екрану:
job.cancel() // Надсилає сигнал скасування, але цикл його ІГНОРУЄ!
```

### ✅ Способи зробити корутину кооперативною (Правильний код)

Щоб важкі цикли та обчислення правильно реагували на скасування, використовують один із трьох варіантів:

#### Спосіб 1: Перевірка прапорця `isActive`
Усередині будь-якої корутини доступна властивість **`isActive`**. Якщо корутину скасували, `isActive` стає `false`:
```kotlin
val job = lifecycleScope.launch(Dispatchers.Default) {
    var count = 0
    for (i in 1..100_000_000) {
        // Якщо корутину скасовано — перериваємо цикл
        if (!isActive) break 
        
        count += i
    }
}
```

#### Спосіб 2: Виклик `ensureActive()` (Рекомендований спосіб)
Метод **`ensureActive()`** — це спеціальне розширення Kotlin, яке перевіряє, чи активна поточна корутина.

**Як це працює під капотом?**
* **Поки корутина активна:** Метод `ensureActive()` абсолютно нічого не робить і дозволяє циклу працювати далі на повній швидкості.
* **Як тільки корутину скасовано (`job.cancel()`):** При наступній ітерації циклу `ensureActive()` виявляє скасування і **миттєво викидає `CancellationException`**. Це негайно перериває виконання циклу та зупиняє корутину.

```kotlin
val job = lifecycleScope.launch(Dispatchers.Default) {
    var count = 0
    for (i in 1..100_000_000) {
        // Якщо корутину скасовано — ensureActive() негайно викине CancellationException,
        // перерве цикл і зупинить корутину, захищаючи процесор від даремної роботи!
        ensureActive() 
        
        count += i
    }
}
```

#### Спосіб 3: Виклик `yield()` (Поступитися місцем)
Метод **`yield()`** — це особлива призупиняюча (`suspend`) функція, яка виконує дві дії одночасно:
1. **Перевіряє скасування:** Якщо корутину скасували, `yield()` відразу викидає `CancellationException`.
2. **Поступається часом виконання:** Вона тимчасово ставить поточну корутину в кінець черги задач її диспатчера, даючи іншим корутинам у цьому ж потоці шанс виконати свій код.

#### Наочний приклад (Чому потрібен `yield()`):
Уявіть, що у вас на Головному потоці (`Dispatchers.Main`) запущено дві паралельні корутини:

```kotlin
// Корутина 1: Тривалий обчислювальний цикл на Main Thread
lifecycleScope.launch(Dispatchers.Main) {
    for (i in 1..1000) {
        // Без yield() Корутина 1 захопить Main Thread і не дасть Корутині 2 виконатися!
        yield() // 1. Перевіряє скасування + 2. Передає квант часу іншим корутинам
        
        processDataChunk(i)
    }
}

// Корутина 2: Термінове оновлення UI
lifecycleScope.launch(Dispatchers.Main) {
    binding.tvStatus.text = "Триває обробка..."
}
```

* **Без `yield()`:** Корутина 1 виконуватиме свій цикл безперервно, і Корутина 2 зможе оновити текст на екрані лише після того, як увесь цикл на 1000 елементів повністю завершиться.
* **З `yield()`:** Після кожного кроку Корутина 1 робить мікропаузу та "поступається місцем", дозволяючи Корутині 2 миттєво оновити статус на екрані.

---

### 🛡️ Гарантоване очищення ресурсів: `NonCancellable`

Коли корутину скасовано, будь-який наступний виклик `suspend` функції всередині неї відразу викидає `CancellationException`. 

Але що робити, якщо у блоці `finally` вам обов'язково потрібно викликати асинхронну функцію для закриття файлу чи сокета? Для цього використовують контекст **`NonCancellable`**:

```kotlin
val job = lifecycleScope.launch {
    try {
        doHeavyWorkWithFile()
    } finally {
        // Блок NonCancellable дозволяє виконувати suspend-функції навіть у скасованій корутині!
        withContext(NonCancellable) {
            closeFileAndCleanup() // Гарантовано виконається до кінця
        }
    }
}
```

## 2. Обробка помилок через `try-catch` та `CancellationException`

Найпростіший спосіб обробити помилку усередині корутини — це класичний блок `try-catch`.

```kotlin
lifecycleScope.launch {
    try {
        val result = fetchDataFromNetwork()
        binding.tvResult.text = result
    } catch (e: Exception) {
        // Перехоплюємо помилку мережі
        binding.tvResult.text = "Помилка завантаження: ${e.message}"
    }
}
```

### Механіка роботи та локація викидання `CancellationException`

При скасуванні корутини ключове значення має розуміння того, **де саме і в який момент** генерується виняток `CancellationException`:

1. **Крок 1: Подача сигналу — виклик `job.cancel()`**  
   Коли ви у своєму коді викликаєте `job.cancel()`, цей виклик сам по собі **не викидає помилку** у поточному потоці. Він лише змінює внутрішній стан об'єкта `Job` на "Скасовано" (`isActive = false`).

2. **Крок 2: Генерація винятку — усередині корутини**  
   Усередині самої корутини виконання триває до **найближчої точки призупинення** (`suspend` функції). Як тільки корутина досягає виклику `delay()`, `withContext()`, `await()` або `ensureActive()`, ця `suspend` функція перевіряє стан `Job`, виявляє прапорець скасування і **викидає `CancellationException` безпосередньо усередині цієї корутини**.

Це дозволяє корутині безпечно зупинити виконання свого коду, розкрутити стек викликів назад та виконати блоки `finally { ... }` для очищення ресурсів.

---

### ⚠️ Критична помилка: Ігнорування `CancellationException`

Оскільки скасування корутини реалізовано саме через виняток **`CancellationException`**, якщо ви у своєму коді перехопите його загальним блоком `catch (e: Exception)` або `catch (e: Throwable)` і **не прокинете (`throw e`) цей виняток далі**, корутина проігнорує сигнал скасування і продовжуватиме працювати!

#### Правильний спосіб обробки:
```kotlin
try {
    fetchDataFromNetwork()
} catch (e: CancellationException) {
    // Обов'язково прокидаємо скасування далі для системи корутин!
    throw e 
} catch (e: Exception) {
    // Обробляємо тільки реальні помилки бізнес-логіки/мережі
    showErrorUI(e)
}
```

### Приклад 1. Наочний приклад роботи `try-catch-finally` при скасуванні:

Розглянемо такий код

```kotlin
val job = lifecycleScope.launch {
    try {
        Log.d(TAG, "1. Початок виконання корутини")
        
        // ⚡ Точка призупинення: при job.cancel() тут викинеться CancellationException
        delay(3000) 
        
        Log.d(TAG, "2. Цей рядок НЕ виконається при скасуванні")
    } catch (e: CancellationException) {
        Log.d(TAG, "3. Спіймали CancellationException! Передаємо скасування далі.")
        throw e // ⚠️ Обов'язково прокидаємо скасування далі для системи!
    } catch (e: Exception) {
        // Обробляємо тільки реальні помилки мережі/бізнес-логіки
        Log.e(TAG, "Помилка завантаження", e)
    } finally {
        Log.d(TAG, "4. Блок очищення ресурсів завжди виконується!")
    }
}

// За потреби скасовуємо корутину:
job.cancel()
```

**Що відбудеться у Logcat при виконанні цього коду:**
1. Надрукується: `"1. Початок виконання корутини"`.
2. Виклик `job.cancel()` перерве `delay(3000)` і викине `CancellationException`.
3. Спрацює блок `catch (e: CancellationException)` і надрукує: `"3. Спіймали CancellationException!..."`.
4. Виконається блок `finally` і надрукує: `"4. Блок очищення ресурсів завжди виконується!"`.
5. Рядок `"2. Цей рядок НЕ виконається при скасуванні"` буде пропущено.

### Приклад 2. Скасування корутини з важкими обчисленнями

А що станеться, якщо `job.cancel()` спрацює **після** того, як `delay()` вже повністю завершив свою роботу?

```kotlin
val job = lifecycleScope.launch {
    try {
        Log.d(TAG, "1. Початок виконання корутини")
        
        delay(1000) // 1. Виконується протягом 1 секунди і успішно завершується!
        
        Log.d(TAG, "2. delay() завершився. Починаємо важкий обчислювальний цикл...")
        
        // 2. Звичайний обчислювальний цикл без suspend-функцій та ensureActive()
        var count = 0
        for (i in 1..100_000_000) {
            count += i
        }
        
        // ⚠️ Цей рядок ВСЕ ОДНО виконається, бо в циклі немає точок перевірки скасування!
        Log.d(TAG, "3. Цикл завершено, count = $count")
    } catch (e: CancellationException) {
        Log.d(TAG, "Спіймали CancellationException")
        throw e
    } finally {
        Log.d(TAG, "4. Блок очищення ресурсів")
    }
}

// Скасовуємо корутину на 1.1 секунді (коли delay(1000) ВЖЕ завершився):
delay(1100)
job.cancel()
```

**Що відбудеться у Logcat при виконанні цього коду:**
1. Надрукується: `"1. Початок виконання корутини"`.
2. Завершиться `delay(1000)` і надрукується: `"2. delay() завершився..."`.
3. Виклик `job.cancel()` на 1.1 сек лише змінить прапорець `isActive = false`. Але оскільки в циклі `for` немає перевірки `ensureActive()`, `CancellationException` **не виникне**.
4. Цикл повністю докрутиться і надрукується: `"3. Цикл завершено..."`.
5. Виконається блок `finally`: `"4. Блок очищення ресурсів"`.

> 💡 **Висновок:** Якщо після `delay()` чи мережевого запиту у вас іде тривала обчислювальна робота, обов'язково додавайте у цикл виклик **`ensureActive()`**, щоб скасування спрацьовувало миттєво!

## 3. Поширення помилок та `SupervisorJob` / `supervisorScope`

За замовчуванням у корутинах діє правило: **якщо впала одна дочірня корутина, вона скасовує свого батька та ВСІХ своїх "братів" (сусідні корутини)**.

### Проблема звичайного `launch`:
```kotlin
// Звичайний Scope: якщо упаде task1, то task2 ТАКОЖ автоматично скасується і впаде весь Scope!
lifecycleScope.launch {
    launch { task1WhichFails() } // Вибиває Exception!
    launch { task2WhichIsImportant() } // Скасовується за компанію!
}
```

### Рішення: `supervisorScope` та `SupervisorJob`
Якщо вам потрібно, щоб помилка в одній корутині **НЕ валила сусідні корутини** (наприклад, якщо не завантажився рекламний банер, список товарів все одно має показатися), використовуйте **`supervisorScope`** або **`SupervisorJob`**.

```kotlin
lifecycleScope.launch {
    // supervisorScope ізолює помилки дочірніх корутин один від одного
    supervisorScope {
        launch {
            try {
                loadAdBanner() // Навіть якщо цей запит впаде...
            } catch (e: Exception) {
                Log.e(TAG, "Баннер не завантажився", e)
            }
        }

        launch {
            loadMainFeed() // ... цей запит УСПІШНО виконається і не скасується!
        }
    }
}
```

## 4. Глобальний обробник `CoroutineExceptionHandler`

**`CoroutineExceptionHandler`** — це спеціальний елемент контексту корутини, який дозволяє перехоплювати **необроблені винятки верхнього рівня** (Top-level Coroutines).

Він діє як "останній рубіж захисту" (catch-all) від крашу застосунку для корутин, запущених через `launch`.

```kotlin
// Створюємо глобальний Handler для помилок
val exceptionHandler = CoroutineExceptionHandler { _, throwable ->
    Log.e(TAG, "Спіймано необроблену помилку у корутині!", throwable)
}

// Передаємо його у запуск корутини
lifecycleScope.launch(Dispatchers.Main + exceptionHandler) {
    val data = fetchDataThatMightCrash() // Якщо тут виб'є краш, додаток не впаде!
}
```

> ⚠️ **Важливо:** `CoroutineExceptionHandler` спрацьовує **тільки** для корутин, запущених через **`launch`** у кореневому Scope. Для корутин, запущених через **`async`**, помилка зберігається всередині `Deferred` і вибиває лише під час виклику **`.await()`** у блоці `try-catch`.

## 5. Порівняння підходів обробки помилок

| Механізм | Коли використовувати | Особливості |
| :--- | :--- | :--- |
| **`try-catch`** | Навколо конкретної `suspend` функції або `.await()`. | Локальна обробка. Пам'ятайте про `CancellationException`! |
| **`supervisorScope`** | Коли запускаєте кілька незалежних корутин поруч. | Помилка в одній корутині не скасовує інші. |
| **`CoroutineExceptionHandler`** | Як глобальний запобіжник від крашу у `launch`. | Працює тільки у верхньому (Top-level) Scope. |

---

## Підсумок

* **Скасування корутин є кооперативним** — корутини перевіряють стан через `isActive` чи `ensureActive()`.
* **`CancellationException`** використовується для скасування корутин — його **не можна ковтати** у `catch (e: Exception)`.
* За замовчуванням падіння однієї дочірньої корутини скасовує всі сусідні корутини та батьківський Scope.
* **`supervisorScope`** та **`SupervisorJob`** ізолюють падіння дочірніх корутин один від одного.
* **`CoroutineExceptionHandler`** слугує глобальним заслоном від крашу додатка для корутин, запущених через `launch`.
